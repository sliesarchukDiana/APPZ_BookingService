***Лабораторна робота №6***

**Adapter**

* **Що:** Інтеграція стороннього API календаря у систему бронювання.
* **Де:** `CalendarAdapter` (адаптер), `ExternalCalendarApi` (адаптований клас), `IBookingProcessor` (цільовий інтерфейс).
* **Як:** `ExternalCalendarApi` має несумісний із системою метод `addEvent()`. `CalendarAdapter` реалізує системний інтерфейс `IBookingProcessor` та перехоплює виклик `createBookingRequest`, конвертуючи отримані аргументи у формат, зрозумілий для `addEvent()`.

**Bridge**

* **Що:** Розділення логіки ініціалізації сповіщень та конкретних каналів їх доставки для уникнення жорсткої прив'язки.
* **Де:** `BookingNotifier` (абстракція), `NotificationSender` (інтерфейс реалізації), `EmailSender`, `SmsSender` (конкретні реалізації).
* **Як:** `BookingNotifier` агрегує об'єкт типу `NotificationSender`. Метод `notifyUser()` виконує базову підготовку і делегує безпосередню відправку методу `send()` конкретної реалізації (email або SMS).


***Лабораторна робота №7***

**Composite**

* **Що:** Побудова деревовидної ієрархії просторів (кімнати та поверхи), з якими клієнтський код працює через єдиний інтерфейс.
* **Де:** `Space` (спільний компонент), `Floor` (контейнер).
* **Як:** `Floor` реалізує `Space` і зберігає колекцію дочірніх об'єктів `Space`. Виклик методу `getDetails()` у `Floor` рекурсивно викликає цей же метод для всіх об'єктів у колекції, незалежно від того, чи це окрема кімната, чи інший поверх.

**Flyweight**

* **Що:** Економія оперативної пам'яті за рахунок спільного використання незмінного стану кімнат (назва типу, місткість).
* **Де:** `RoomType` (стан / пристосуванець), `RoomTypeFactory` (фабрика).
* **Як:** Замість створення нових об'єктів конфігурації для кожної кімнати, `RoomTypeFactory` перевіряє у словнику наявність уже створеного об'єкта `RoomType` за складеним ключем. Якщо об'єкт існує — повертається посилання на нього, якщо ні — створюється новий, зберігається в кеш і повертається.


***Лабораторна робота №8***

**Decorator**

* **Що:** Динамічне додавання нових обов'язків (послуг кейтерингу) до існуючого об'єкта бронювання без зміни його базового коду.
* **Де:** `IBooking` (компонент), `BookingDecorator` (базовий декоратор), `CateringDecorator` (конкретний декоратор).
* **Як:** `CateringDecorator` обгортає екземпляр `IBooking`. У перевизначеному методі `confirm()` він спочатку викликає базове підтвердження (`super.confirm()`), а потім виконує власну розширену логіку (`addCatering()`).

**Proxy**

* **Що:** Контроль доступу до центрального обробника бронювань, фільтрація неавторизованих запитів.
* **Де:** `BookingProcessorProxy` (заступник), `BookingController` (реальний об'єкт).
* **Як:** Проксі реалізує інтерфейс `IBookingProcessor` та містить посилання на `BookingController`. Метод `createBookingRequest` у проксі перехоплює запит, виконує перевірку прав методу `hasAccess()` (відсіює користувачів з ID "GUEST"), і лише після успішної перевірки передає виконання реальному об'єкту. В іншому випадку запит блокується.
