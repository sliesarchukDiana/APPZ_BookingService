<h2>Опис паттернів у проєкті</h2>

<h3>***Лабораторна робота №1-2***</h3>

* **Dependency Inversion Principle (DIP) / SOLID:** Застосовано при створенні інтерфейсу `IBookingProcessor`. Класи не залежать від конкретних реалізацій обробника бронювань (наприклад, `BookingController` або `CalendarAdapter`), а залежать від абстракції `IBookingProcessor`.   
* **High Cohesion (Висока зв'язність) / GRASP:** Клас `User` відповідає лише за зберігання та надання базових даних користувача, виконуючи одне логічне завдання, що забезпечує його вузьку спрямованість.   
* **Controller (Контролер) / GRASP:** `BookingController` виконує роль контролера (як Одинак), який координує обробку запитів на створення бронювання (`createBookingRequest`) у системі.

<hr>

<h3>***Лабораторна робота №3***</h3>

**Singleton (Одинак)**

* **Що:** Гарантує існування лише одного екземпляра класу в системі та надає глобальну точку доступу до нього.   
* **Де:** Клас `BookingController`.   
* **Як:** Клас має приватний конструктор, щоб запобігти створенню об'єктів ззовні. Доступ до єдиного екземпляра забезпечується через статичний метод `getInstance()`, який реалізує "ліниву ініціалізацію" (об'єкт створюється лише при першому зверненні).   

**Prototype (Прототип)**

* **Що:** Дозволяє створювати нові об'єкти шляхом копіювання існуючих (прототипів) без прив'язки до деталей їх створення.   
* **Де:**  Клас `Room`.   
* **Як:** Клас реалізує стандартний інтерфейс `Cloneable`. Метод `clone()` перевизначається для створення та повернення копії поточного екземпляра кімнати з усіма її поточними характеристиками.

<hr>

<h3>***Лабораторна робота №4***</h3>

**Factory Method (Фабричний метод)**

* **Що:** Визначає інтерфейс для створення об'єкта, але дозволяє підкласам вирішувати, який клас інстанціювати.   
* **Де:** Інтерфейс `RoomFactory` та клас `ConferenceRoomFactory`.   
* **Як:** `RoomFactory` оголошує метод `createRoom(String id)`. `ConferenceRoomFactory` реалізує цей метод, створюючи та повертаючи конкретний тип кімнати — Room із заздалегідь визначеною назвою ("Conference Room") та місткістю.   

**Abstract Factory (Абстрактна фабрика)**
* **Що**: Надає інтерфейс для створення сімейств пов'язаних або залежних об'єктів (наприклад, кімнат і відповідного обладнання) без вказівки їхніх конкретних класів.   
* **Де**: Інтерфейс `FacilityFactory`, клас `VIPFacilityFactory`, інтерфейс `Equipment`, клас `Projector`.   
* **Як:** `FacilityFactory` визначає два методи: `createRoom()` та `createEquipment()`. `VIPFacilityFactory` реалізує їх для створення узгодженої конфігурації для VIP-обслуговування, повертаючи VIP-кімнату та конкретне обладнання Projector.

<hr>

<h3>***Лабораторна робота №5***</h3>

**Builder (Будівельник)**

* **Що:** Дозволяє покроково створювати складні об'єкти (у цьому випадку — бронювання), відокремлюючи процес конструювання від їхнього представлення.   
* **Де**: Клас `Booking` та його вкладений статичний клас `Builder`.   
* **Як**: `Builder` містить методи для налаштування окремих частин бронювання (room(), user(), time()), які повертають сам об'єкт `Builder` (fluent interface). Метод `build()` фіналізує процес і створює об'єкт `Booking`.   

**Object Pool (Пул об'єктів)**

* **Що:** Покращує продуктивність за рахунок повторного використання заздалегідь створених об'єктів (кімнат) замість постійного їх створення та знищення.   
* **Де:** Клас `RoomPool`.   
* **Як:** У конструкторі `RoomPool` створюється задана кількість екземплярів `Room`, які зберігаються у черзі (Queue). Клієнт отримує кімнату через метод `acquireRoom()` і після використання повертає її назад у пул за допомогою releaseRoom().

<hr>

<h3>***Лабораторна робота №6***</h3>

**Adapter**

* **Що:** Інтеграція стороннього API календаря у систему бронювання.
* **Де:** `CalendarAdapter` (адаптер), `ExternalCalendarApi` (адаптований клас), `IBookingProcessor` (цільовий інтерфейс).
* **Як:** `ExternalCalendarApi` має несумісний із системою метод `addEvent()`. `CalendarAdapter` реалізує системний інтерфейс `IBookingProcessor` та перехоплює виклик `createBookingRequest`, конвертуючи отримані аргументи у формат, зрозумілий для `addEvent()`.

**Bridge**

* **Що:** Розділення логіки ініціалізації сповіщень та конкретних каналів їх доставки для уникнення жорсткої прив'язки.
* **Де:** `BookingNotifier` (абстракція), `NotificationSender` (інтерфейс реалізації), `EmailSender`, `SmsSender` (конкретні реалізації).
* **Як:** `BookingNotifier` агрегує об'єкт типу `NotificationSender`. Метод `notifyUser()` виконує базову підготовку і делегує безпосередню відправку методу `send()` конкретної реалізації (email або SMS).

<hr>

<h3>***Лабораторна робота №7***</h3>

**Composite**

* **Що:** Побудова деревовидної ієрархії просторів (кімнати та поверхи), з якими клієнтський код працює через єдиний інтерфейс.
* **Де:** `Space` (спільний компонент), `Floor` (контейнер).
* **Як:** `Floor` реалізує `Space` і зберігає колекцію дочірніх об'єктів `Space`. Виклик методу `getDetails()` у `Floor` рекурсивно викликає цей же метод для всіх об'єктів у колекції, незалежно від того, чи це окрема кімната, чи інший поверх.

**Flyweight**

* **Що:** Економія оперативної пам'яті за рахунок спільного використання незмінного стану кімнат (назва типу, місткість).
* **Де:** `RoomType` (стан / пристосуванець), `RoomTypeFactory` (фабрика).
* **Як:** Замість створення нових об'єктів конфігурації для кожної кімнати, `RoomTypeFactory` перевіряє у словнику наявність уже створеного об'єкта `RoomType` за складеним ключем. Якщо об'єкт існує — повертається посилання на нього, якщо ні — створюється новий, зберігається в кеш і повертається.

<hr>

<h3>***Лабораторна робота №8***</h3>

**Decorator**

* **Що:** Динамічне додавання нових обов'язків (послуг кейтерингу) до існуючого об'єкта бронювання без зміни його базового коду.
* **Де:** `IBooking` (компонент), `BookingDecorator` (базовий декоратор), `CateringDecorator` (конкретний декоратор).
* **Як:** `CateringDecorator` обгортає екземпляр `IBooking`. У перевизначеному методі `confirm()` він спочатку викликає базове підтвердження (`super.confirm()`), а потім виконує власну розширену логіку (`addCatering()`).

**Proxy**

* **Що:** Контроль доступу до центрального обробника бронювань, фільтрація неавторизованих запитів.
* **Де:** `BookingProcessorProxy` (заступник), `BookingController` (реальний об'єкт).
* **Як:** Проксі реалізує інтерфейс `IBookingProcessor` та містить посилання на `BookingController`. Метод `createBookingRequest` у проксі перехоплює запит, виконує перевірку прав методу `hasAccess()` (відсіює користувачів з ID "GUEST"), і лише після успішної перевірки передає виконання реальному об'єкту. В іншому випадку запит блокується.
